阶段 1

领域模型与核心 Web 流程

目标：先把最小业务闭环跑通：选设备 → 创建巡检 → 校验 → 提交 → 在 Pinia 内存中形成巡检记录。

核心流程

设备列表
  ↓
设备详情
  ↓
创建巡检
  ↓
InspectionDraft
  ↓
基础校验
  ↓
InspectionRecord
  ↓
Pinia records[]

你需要完成什么

任务真正含义关注点
稳定设备列表和详情保证 DeviceList → DeviceDetail 路由和数据查询稳定直接输入详情 URL 也能正常处理
定义巡检草稿描述“用户正在填写”的数据Draft 不等于正式业务记录
定义巡检记录描述“提交后”的正式数据增加 id、createdAt 等正式字段
创建巡检页面表单输入、结果选择、备注等页面只负责交互，不要塞太多业务逻辑
提交到 Piniarecords.push(record)先做内存闭环，不急着做数据库
这一阶段重点关注：数据模型比页面更重要。先分清 Device、InspectionDraft、InspectionRecord 三个概念。

你要记录的知识点

  • Draft 表示编辑中的临时状态，Record 表示提交后的正式业务数据。
  • Pinia 负责当前运行时状态。
  • 页面通过 Store 操作业务数据，不要每个页面各自维护一份记录。
  • 先形成最小闭环，再逐渐加持久化、照片、网络等能力。
阶段验收：选择一台设备 → 填巡检 → 提交 → records[] 新增一条记录。
面试表达：我先定义巡检领域模型，通过设备详情进入巡检创建页，使用 Draft 承载表单状态，完成基础校验后转换为 InspectionRecord，并提交到 Pinia Store，形成最小业务闭环。
阶段 2

Preferences 与巡检历史

目标：解决“刷新/关闭 App 后 Pinia 数据全部消失”的问题，并完成巡检历史浏览。

核心流程

InspectionRecord[]
       ↓
JSON.stringify()
       ↓
Capacitor Preferences
       ↓
App 关闭 / 重启
       ↓
Preferences.get()
       ↓
JSON.parse()
       ↓
恢复 Pinia
       ↓
历史列表 → 历史详情

你需要完成什么

任务真正含义关注点
持久化记录元数据把 records 转成 JSON 存入 PreferencesPreferences 适合小型结构化数据
启动恢复数据App 初始化时读取本地 JSON 并灌回 Pinia理解 hydration / 状态恢复
历史列表展示 records[]页面读取 Store，不直接读取 Preferences
历史详情按 id 查找某条记录和 Device Detail 的查询模式相似
JSON 损坏JSON.parse 可能抛异常必须容错，不能让 App 启动失败
数据版本为未来字段变化留下兼容空间考虑 version / migration
这一阶段重点关注：Pinia = 运行时状态，Preferences = 持久化状态。页面不要直接操作 Native Storage。

推荐分层

Vue Page
   ↓
Inspection Store
   ↓
inspection-storage.service.ts
   ↓
Capacitor Preferences

你要记录的知识点

  • JSON.stringify()：对象/数组 → 字符串。
  • JSON.parse()：字符串 → 对象/数组。
  • 本地 JSON 也要当成“不可信输入”，读取时必须有异常处理。
  • 发生解析错误时，可以回退为空数组，同时通过日志保留错误信息。
  • 数据长期存在后要考虑 schema/version 变化。
常见坑：不要让 InspectionHistory.vue 自己调用 Preferences.get()，否则状态来源会变乱。
阶段验收：提交巡检 → 完全关闭 App → 再打开 → 历史记录依然存在并能查看详情。
面试表达：巡检记录运行时由 Pinia 管理，提交后通过 Preferences 持久化。App 启动时统一恢复到 Store，同时对 JSON 损坏和数据版本做了容错设计。
阶段 3

Camera、Filesystem 与 Android 权限

目标：让用户拍摄现场照片，把图片真正保存到 App 本地文件系统，并让历史记录长期引用这些图片。

核心流程

创建巡检
   ↓
Camera.getPhoto()
   ↓
临时照片 / URI
   ↓
Filesystem.writeFile()
   ↓
长期保存的图片文件
   ↓
得到 photoPath
   ↓
InspectionRecord 保存 photoPath
   ↓
Preferences 保存记录元数据

必须分清两种存储

能力存什么不要存什么
Preferencesid、deviceId、result、remark、photoPath大图片/Base64 大数据
Filesystemjpg/png 等真实文件业务结构化元数据
这一阶段最关键的设计：业务记录只保存“文件引用”，即 photoPath；真正的图片文件交给 Filesystem。

异常分支一定要做

taking photo
 ├─ 成功 → saving
 ├─ 用户取消 → 回到 idle
 ├─ 权限拒绝 → permissionDenied
 └─ 相机异常 → error

saving file
 ├─ 成功 → photoPath
 └─ 写入失败 → error，不保存假的 photoPath

你要记录的知识点

  • Camera 负责“获取照片”，Filesystem 负责“长期保存照片”。
  • 拍照成功不代表整个流程成功，Filesystem 写入也必须成功。
  • 用户取消 ≠ 系统异常，不应该用错误弹窗吓用户。
  • Native 权限永远不能假设一定会被用户授予。
  • 读取历史详情时，通过 photoPath 找回文件并展示。

推荐分层

InspectionCreate.vue
       ↓
inspection-photo.service.ts
       ↓
 ┌─────────────┐
 ↓             ↓
Camera      Filesystem
阶段验收：真机拍照 → 保存 → 提交 → 历史详情能显示 → 杀掉 App 后重开，图片仍然存在。
面试表达：我通过 Capacitor Camera 获取现场照片，再使用 Filesystem 持久化到应用本地目录，巡检记录只保存文件路径引用，并处理了取消、权限拒绝和文件写入失败。
阶段 4

Device、Network 与 Local Notifications

目标：让 App 能感知当前设备、网络状态，并在离线情况下继续工作，同时为巡检任务安排本地提醒。

四块能力

Device
→ 我运行在哪台设备上？

Network
→ 我现在有没有网络？

Preferences / Filesystem
→ 没网时还能不能浏览本地数据？

Local Notifications
→ 到时间能不能提醒用户？

你需要完成什么

模块任务关注点
Device系统信息页型号、平台、系统版本、制造商等
Network初始查询 + 状态监听getStatus 和 addListener 是两件事
Offline断网后继续浏览本地数据离线 ≠ 整个 App 不可用
Notification权限申请 + 定时提醒最好和巡检任务本身绑定

Network 的正确理解

App 启动
  ↓
Network.getStatus()
  ↓
得到初始 isOnline

App 运行中
  ↓
Network.addListener()
  ↓
Wi-Fi / 移动网络变化
  ↓
更新 networkStore
  ↓
Vue UI 自动响应
这一阶段重点关注：Network Listener 是长期监听，要考虑注册和清理；Offline-first 的核心不是“没网禁用 App”，而是“本地能力继续工作，只有远程能力受限”。

本地通知要和业务生命周期关联

创建任务
 ↓
schedule notification

修改提醒时间
 ↓
cancel old + schedule new

删除任务
 ↓
cancel notification

你要记录的知识点

  • Device 能力是 Hybrid App 与普通网页的重要区别之一。
  • 网络状态应该进入 Store，让多个页面共享。
  • 全局离线提示可以放在 App.vue，例如 NetworkBanner。
  • Local Notification 是本地安排，不等于服务器 Push。
  • 任务和 Notification 最好保存关联 id，便于修改/删除时同步取消。
阶段验收：关闭网络 → 页面立即显示离线 → 历史和图片仍能浏览；创建提醒 → App 退后台后 Android 能按时弹通知。
面试表达：我通过 Network Plugin 将 Android 网络状态映射到 Pinia，并设计本地优先访问，使离线情况下仍可浏览巡检记录；同时用 Local Notifications 将提醒和巡检任务生命周期关联。

Android Studio 与真机要关注什么

  • Vue 层问题：Chrome DevTools / console。
  • Android Native 层问题：Android Studio Logcat。
  • 改完 Web 代码后，注意重新 build / sync，否则手机可能仍运行旧资源。
  • 必须验证 Camera、Filesystem、Preferences、Network、Notifications 的真机行为。

你最需要记住的 15 句话

  1. Draft 是编辑状态，Record 是正式业务数据。
  2. Pinia 管运行时状态，Preferences 管跨重启持久化。
  3. 页面尽量只认 Store，不直接操作 Native Storage。
  4. JSON.parse 可能失败，本地数据也必须做容错。
  5. 长期存在的数据要考虑 version 和迁移。
  6. Camera 负责拿照片，Filesystem 负责长期保存。
  7. 业务记录存 photoPath，不把大图片塞进 Preferences。
  8. 用户取消和真正异常要区分。
  9. Native 权限不能假设一定会授予。
  10. Network 要先查询当前状态，再监听后续变化。
  11. 离线不等于 App 不可用，本地能力应该继续工作。
  12. Local Notification 要和任务生命周期保持一致。
  13. Hybrid 调试同时包含 Web 层和 Android Native 层。
  14. Debug 是开发测试，Release 是给别人安装/发布。
  15. 面试讲项目时用“业务问题 → 技术方案 → 异常处理 → 验证结果”。
