一、30 秒项目介绍

我独立实现了一个面向现场设备巡检的 Android Hybrid App。前端使用 Vue 3、TypeScript、Pinia 和 Vue Router，端侧通过 Capacitor 接入系统相机、私有文件存储、Preferences、Device、Network 和 Local Notifications。项目重点是把相机临时照片复制到 App 私有目录，再将稳定文件路径与类型安全的巡检记录一起持久化；应用冷启动后，记录和照片仍然存在。最后我使用自建 keystore 构建并验证了签名 Release APK 与 AAB，且在 Android 真机完成了 Release 冒烟测试。
业务价值

可追溯的巡检闭环

从设备详情创建巡检，填写结果与备注，附加现场照片，在历史中按设备和时间回看记录。

Vue 页面负责交互；Composable 组织页面逻辑；Service 隔离 Capacitor 插件调用与持久化细节。

三、架构：如何从页面走到原生能力

项目采用“页面 / Composable / Service / Capacitor Plugin”的分层。这样页面不直接了解 Android URI、插件选项或文件路径策略，后续替换实现和定位问题都更容易。

Vue View→Composable→Domain / Storage Service→Capacitor Plugin→Android 系统能力

领域层

InspectionDraft 表示尚未提交的表单状态；InspectionRecord 是合法、可保存的巡检历史实体，包含 ID、创建时间与持久照片路径。

状态与存储层

Pinia 提供当前进程内的响应式列表；Preferences 保存版本化 JSON 载荷。写入成功后才更新 Pinia，避免 UI 出现“假成功”。

一次带照片的巡检提交数据流

设备详情页 → 巡检表单（InspectionDraft） → Camera.takePhoto() 取得临时照片 → 预览 temporaryPhotos（仅内存、临时 URI） → 提交开始时复制 photosToPersist 快照 → Filesystem.copy() 到 Directory.Data/inspection-photos/ → 创建 InspectionRecord（photoPaths 使用 durable file:// URI） → Preferences 持久化成功 → Pinia 更新，巡检历史响应式展示

Day 4 运行环境与通知流

HomeView → useNativeEnvironment → Device.getInfo() + Network.getStatus() → Network.addListener() → 网络切换时响应式更新；InspectionFormView 保存成功 → useInspectionNotification → checkPermissions() / requestPermissions() → LocalNotifications.createChannel() → LocalNotifications.schedule() → Android 系统通知栏

四、模块拆解：面试可讲的关键决策

Day 1

类型安全的巡检领域模型

问题：表单输入未必合法，不应直接当成历史记录保存。

决策：用不同类型区分草稿和最终记录，在 Service 边界创建 UUID、ISO 时间和合法记录。

可讲价值：类型建模、提交边界、避免让页面随意拼装持久化实体。

Day 2

Preferences 的可靠持久化

问题：本地 JSON 可能为空、损坏，写入也可能失败。

决策：以 unknown 接收解析结果并进行运行时校验；使用版本化载荷 { version, records }。

可讲价值：TypeScript 只能约束编译期，外部数据仍必须在运行时验证。

Day 3 Task 3

相机临时态与取消语义

问题：相机返回的是临时资源，用户取消拍摄不是系统异常。

决策：通过 Camera Service 与 Composable 隔离插件；以 { status: 'cancelled' } 建模取消，而不是抛出错误。

可讲价值：正常用户分支与真正错误分支分开处理，页面逻辑更清晰。

Day 3 Task 4

临时照片变为持久资产

问题：相机缓存可能被系统清理，不能把临时路径直接持久化。

决策：拷贝到 App 私有的 Directory.Data，记录中只保存 durable file:// URI。

可讲价值：理解缓存、私有存储、持久化路径与 Android 权限边界。

五、核心追问：建议的回答结构

1. 为什么不直接将相机返回的路径保存到 Preferences？

相机返回的路径可能指向缓存目录，缓存资源会被系统清理，应用重启后也不应假设一定存在。因此我把它当作临时态：预览时使用 webPath，提交时通过 Filesystem 拷贝到 App 私有 Directory.Data，最终记录保存的是可长期使用的 file:// URI。

2. 为什么 Pinia 和 Preferences 都需要？

Pinia 负责当前运行进程的响应式 UI 状态；Preferences 负责 App 退出或被杀后仍可恢复的数据。两者职责不同。写入 Preferences 成功后再更新 Pinia，能避免持久化失败却先在 UI 中显示成功。

3. Filesystem 文件写成功、Preferences 写失败时如何处理？

当前实现是补偿式一致性：先复制临时照片，再尝试保存巡检记录；如果记录创建或 Preferences 保存失败，就删除本次刚复制出的文件。它不是数据库事务；如果进程在两步之间被系统杀死，仍可能出现孤儿文件。后续可加启动时清理或暂存目录加提交标记。

4. 为什么相机不需要在页面里直接申请 CAMERA 权限？

当前配置通过 Capacitor 打开系统相机 Activity，且 saveToGallery: false。应用没有直接访问公共相册或自行接管相机硬件，因此本方案不需要页面中直接处理 CAMERA 或外部存储权限。未来接入媒体库、公开相册或通知功能时，会按对应插件和 Android 版本处理权限。

5. 为什么只禁用按钮还不够？

按钮禁用是 UI 层防护，避免用户继续操作；异步任务则应在开始时拥有明确、稳定的业务输入。因此还要复制 const photosToPersist = [...temporaryPhotos.value]。后续文件保存依赖这份快照，而不是依赖可能变化的响应式数组。

6. 为什么既要调用 Network.getStatus()，又要 addListener()？

getStatus() 提供进入页面时的当前快照；addListener('networkStatusChange') 处理之后的 Wi-Fi、移动网络和离线变化。只用前者会状态过期，只用后者会缺少首屏状态。监听器在页面卸载时移除，避免重复回调和内存泄漏。

7. 为什么通知失败不能让巡检提交失败？

巡检记录写入 Preferences 才是主业务成功标准；本地通知是保存成功后的用户体验增强。权限拒绝或通知调度异常都应单独反馈，不能回滚已持久化的记录。

8. 为什么 Release APK 不能覆盖 Debug APK？

Android 用包名和签名证书共同判断是否为合法更新。当前 Debug 包使用 Android Debug Keystore，Release 包使用自建 Release Keystore，证书不同，因此必须先卸载 Debug 包或使用不同 applicationId。项目最终选择保留正式包名并卸载 Debug 后安装 Release。

  1. 开场（20 秒）：展示首页运行环境，说明这是已安装在 Android 真机上的签名 Release App，并展示真实设备与网络状态。
  2. 业务流（35 秒）：进入设备详情，发起巡检，选择结果、填写备注，说明草稿与正式记录在类型上分离。

八、当前边界与诚实说明

项目已完成最初定义的核心 Hybrid 能力与 Release 交付，但它仍是端侧离线优先的求职项目，不应被包装成已上线的生产巡检平台。
  • 已知技术债：若照片复制完成但 Preferences 写入前进程被杀，可能产生孤儿文件；现有补偿删除只能覆盖可捕获的失败。
  • Release 加固：未来应让 Gradle 在缺少或填写不完整的 keystore.properties 时明确阻止 Release 构建，防止误生成未签名产物。
  • 展示边界：历史列表目前显示照片数量，尚未做持久照片缩略图墙。
  • 网络层：设备数据目前由有模拟延迟的 Service 提供，未为了技术栈清单而强行引入 Axios。接入真实后端时，再封装请求实例、超时、拦截器和离线同步队列。
  • Android 13+ 实机：通知权限申请逻辑与 Manifest 已实现；当前真机是 Android 10，因此未能实际看到 Android 13+ 的授权弹窗。
