三、正式 Code Review：先审查，不直接修改

Review 的目的不是“挑毛病”，而是用团队协作和生产项目的标准，确认当前项目的可靠性与边界。完成 Review 后，再为每一项建议决定：立即修、记录后续、或明确不做。

规则：在 Review 报告输出前，不因为“看起来更优雅”而重构。先收集证据、说明影响、给出选项，再决定是否改变代码。
维度审查问题你需要能说的话
架构View、Store、Service、Capacitor Plugin 的职责是否单一？依赖是否从页面流向服务？“原生调用被收敛在 Service，页面只处理展示与交互。”
TypeScript外部 JSON 是否先按 unknown 校验？是否存在隐式 any？业务状态是否有联合类型？“类型断言不等于运行时可信，所以持久化数据先校验。”
Vuecomputed、watch、生命周期与响应式状态是否有清晰用途？事件是否解绑？“详情记录由路由 id 与 Store 数据共同派生，避免重复状态。”
Pinia初始化、保存失败、重复提交与错误状态是否有统一入口？“Pinia 管运行时响应式状态，Preferences 管跨重启持久化。”
异常处理权限拒绝、文件复制失败、目录已存在、图片丢失、持久化失败如何降级？“关键 Native 操作都有业务错误边界，失败不会让页面整体失效。”
可维护性是否有重复逻辑、隐含平台假设、难以测试的耦合？“我会区分当前 MVP 边界和真正需要立即修复的风险。”

四、项目讲解稿：准备三种长度

不要背功能清单。每次介绍都要同时包含：业务目标、关键技术、真实挑战、最终交付和当前边界。

1. 30～45 秒电梯版

我做的是 Device Inspector，一款基于 Vue 3、TypeScript 和 Capacitor 的 Android Hybrid 设备巡检应用。

它支持设备查看、创建巡检、原生相机拍照、巡检历史本地持久化、离线照片回看、网络与设备信息展示和本地通知。项目的重点不是页面数量，而是把 Vue 的状态管理和 Capacitor 原生能力做分层集成，并最终构建成签名 Release APK，在 Android 真机完成验证。

2. 2～3 分钟标准版结构

  1. 场景：现场人员需要围绕具体设备创建巡检、拍摄现场照片，并在无网络环境中回看记录。
  2. 技术选型：Vue 3 + TypeScript 负责业务 UI；Pinia 管状态；Capacitor 连接 Android Native 能力。
  3. 核心链路：设备详情 → 巡检草稿 → 原生相机 → 提交边界 → Preferences / Filesystem → 历史与照片预览。
  4. 分层：View → Store → Service → Capacitor Plugin，避免 Native 调用散落在页面。
  5. 难点：Android 文件目录已存在时 mkdir 仍可能失败，导致照片提交失败；通过先 stat、按需创建、失败后再次确认实现幂等初始化。
  6. 交付与边界：已打签名 Release APK / AAB 并真机验证；当前本地优先，尚未实现服务端同步。

A. Vue 3

为什么详情页的记录使用 computed 派生，而不是加载时复制一份普通变量？

答题要点：computed(() => getRecordById(props.id)) 同时依赖路由参数与 Pinia records。当路由切换或 Store 恢复持久化数据后，详情会自动更新；复制到局部变量会产生重复状态和同步风险。

computed 和 watch 如何取舍？

答题要点：computed 用于从已有响应式数据派生值，例如当前记录、照片展示项；watch 用于副作用，例如记录变化后加载关联设备、路由变更后清空预览状态。

为什么要在组件卸载时清理键盘事件？

答题要点：预览层监听了全局 Escape 键。若不在 onBeforeUnmount 移除监听，路由离开后仍可能触发旧逻辑，造成内存泄漏和错误交互。

B. TypeScript

为什么 Preferences 读取的 JSON 不能直接断言为 InspectionRecord[]？

答题要点：JSON.parse 成功只能说明 JSON 格式正确，不代表业务结构可信。持久化数据属于外部输入，应先按 unknown 处理，经运行时校验后才进入应用内部状态。

为什么区分 InspectionDraft 和 InspectionRecord？

答题要点：Draft 是表单编辑期的临时状态，可以不完整；Record 是完成校验、拥有 ID、时间和持久化照片路径的可靠业务实体。转换边界阻止非法草稿直接进入历史数据。

unknown 和 any 的根本区别是什么？

答题要点：any 关闭类型检查，风险向后扩散；unknown 强制在使用前缩窄类型，适合 Native Plugin 异常、JSON、第三方返回值等不可信边界。

C. Pinia 与本地持久化

Pinia、Preferences、Filesystem 分别负责什么？

答题要点：Pinia 管运行期响应式状态；Preferences 存小体积结构化 JSON，跨重启恢复巡检记录；Filesystem 存较大的照片文件。记录中只保存文件 URI，实现元数据与文件分离。

为什么不把照片转 Base64 存进 Preferences？

答题要点：Base64 会增加体积，Preferences 不适合大二进制内容，也会导致序列化、读取和内存压力上升。正确做法是文件落 Filesystem，记录只保留 URI。

D. Capacitor / Android

为什么相机临时照片需要复制到 Directory.Data？

答题要点：Camera 返回的位置可能是系统或应用缓存，缓存可被清理；提交时复制到应用私有数据目录后，才适合作为巡检历史的长期引用，离线和重启后仍可回看。

为什么历史照片展示前要调用 Capacitor.convertFileSrc？

答题要点：Filesystem 返回的是原生文件 URI；Vue 页面运行在 Android WebView 中，不能直接假设能加载 file://。该方法把原生 URI 转为 WebView 可访问 URL。转换收敛在 Service，页面不直接依赖平台细节。

你如何处理 Android mkdir 的“目录已存在”问题？

答题要点：先用 Filesystem.stat 探测；目录存在则直接返回；不存在才 mkdir；mkdir 报错后再探测一次目录，因为并发请求可能已由另一条请求创建成功。这样目录初始化具备幂等性。

E. 项目演进

如果接入服务端同步，你会怎么设计？

答题要点：保持本地优先：记录先写本地；增加同步状态和任务队列；Network 恢复后上传照片再提交元数据；失败指数退避重试；服务端返回版本号或更新时间用于冲突处理；登录鉴权与 Token 刷新单独封装。

当前有哪些明确不做的边界？

答题要点：没有云同步、登录权限、后台孤儿文件清理、手势缩放图库和自动化端到端测试。不是忽略，而是 MVP 为保证可解释、可验证、可交付而有意控制范围；每项都有后续演进方向。
