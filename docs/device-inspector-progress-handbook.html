模块 1：巡检领域类型——草稿与正式记录

解决的问题

正在填写的表单允许暂时不完整；进入历史的数据必须完整。两者不能用一个“所有字段可选”的接口混在一起。

type InspectionResult =
  | 'passed'
  | 'issue_found'

interface InspectionDraft {
  deviceId: string
  inspectorName: string
  result: InspectionResult | null
  notes: string
  photoPaths: string[]
}

interface InspectionRecord {
  id: string
  deviceId: string
  inspectorName: string
  result: InspectionResult
  notes: string
  photoPaths: string[]
  inspectedAt: string
}

草稿允许

  • result: null
  • 巡检人暂时为空字符串
  • 没有 ID
  • 没有最终巡检时间

正式记录要求

  • 结果必须是合法联合类型
  • ID 必须存在
  • 巡检时间必须存在
  • 可以进入历史和持久化

面试必须能说

Partial<InspectionRecord> 会让所有字段都可能不存在，无法准确表达表单草稿的稳定结构；显式 Draft/Record 虽有少量重复，但业务语义更强。

  • src/types/inspection.ts
模块 2：类型安全的 Vue 巡检表单

核心选择

草稿暂时只在当前页面消费，因此使用页面局部的 reactive<InspectionDraft>，没有过早把所有输入字段放进 Pinia。

const draft = reactive<InspectionDraft>(
  createDraft(props.id),
)

运行时规则

  • 巡检人不能只有空格。
  • 必须选择巡检结果。
  • 选择“发现问题”时必须填写问题说明。
  • Camera 区域只是占位，不伪造原生能力。

路由复用保护

watch(
  () => props.id,
  (nextId) => {
    Object.assign(draft, createDraft(nextId))
    void deviceStore.loadDeviceById(nextId)
  },
  { immediate: true },
)

设备 ID 变化时重置草稿，防止设备 A 的备注和结果污染设备 B。

面试必须能说

状态是否进入 Pinia，要看生命周期和消费者范围；不是所有 ref/reactive 都应该全局化。

  • src/views/InspectionFormView.vue
  • src/router/index.ts
  • src/views/DeviceDetailView.vue
模块 3：提交边界与 Pinia 内存记录

为什么页面不能直接 push

草稿可能不完整，也没有 ID 和时间。提交边界统一完成校验、标准化和实体创建，Store 只接收合法正式记录。

type InspectionRecordCreationResult =
  | { success: true; record: InspectionRecord }
  | {
      success: false
      errors: InspectionValidationErrors
    }

创建记录时做了什么

  • trim() 清理巡检人和备注。
  • crypto.randomUUID() 生成实体 ID。
  • new Date().toISOString() 生成标准时间。
  • [...draft.photoPaths] 避免草稿与历史共享可变数组。

Pinia 的角色

const records = ref<InspectionRecord[]>([])
const recordCount = computed(
  () => records.value.length,
)

当时这一步只有内存状态：路由跳转保留，页面刷新丢失。这个限制随后由 Preferences 模块解决。

  • src/services/inspectionService.ts
  • src/stores/inspectionStore.ts
模块 4：巡检历史、设备关联与日期工具

展示层关联

巡检记录只保存 deviceId，历史页面用 Device Store 建立当前设备信息关联。

const deviceById = computed(
  () => new Map(
    devices.value.map(
      (device) => [device.id, device],
    ),
  ),
)

const historyItems = computed(() =>
  records.value.map((record) => ({
    record,
    device:
      deviceById.value.get(record.deviceId)
      ?? null,
  })),
)

为什么允许设备为 null

  • 设备接口可能失败。
  • 设备可能已经删除。
  • 旧记录可能关联未知设备。
  • 历史主数据仍可回退显示 deviceId。

日期集中处理

第三个页面需要日期展示时，提取 formatDateTime()，同时处理空值和非法日期，不引入日期库。

当前语义

历史显示设备“当前名称和位置”。如果生产审计要求保留巡检当时的设备信息，应改为保存 deviceSnapshot。

  • src/views/InspectionHistoryView.vue
  • src/utils/date.ts
模块 5：Capacitor Preferences 持久化

存储格式

{
  "version": 1,
  "records": [
    {
      "id": "inspection-...",
      "deviceId": "dev-001",
      "inspectorName": "赵六",
      "result": "passed",
      "notes": "",
      "photoPaths": [],
      "inspectedAt": "2026-08-09T07:35:10.000Z"
    }
  ]
}

为什么 JSON.parse 后是 unknown

TypeScript 接口不会验证本地 JSON。当前代码把解析结果视为 unknown，再检查对象、版本、数组和每个字段，不用 as InspectionRecord[] 假装安全。

一致性策略

const nextRecords = [
  creationResult.record,
  ...records.value,
]

await saveInspectionRecords(nextRecords)
records.value = nextRecords

先写 Preferences，成功后更新 Pinia。写入失败时，界面不会显示一条实际上没有落盘的记录。

真实验证

  • 刷新后记录仍存在。
  • Web key 为 CapacitorStorage.device-inspector.inspection-records。
  • 损坏 JSON 会显示可重试错误。
  • 恢复原 payload 后记录重新出现。
  • 模拟写入失败时，Pinia 数量不会增加。

限制

所有记录保存在一个 JSON 字符串中，适合小型求职项目；大量记录、复杂查询和分页应迁移到 SQLite。

阶段 Code Review

这里列出当前做得正确的部分、已知限制和后续必须处理的风险。

1. 架构审查

正确点

  • 页面、Store、Domain Service、Storage Service、Plugin 职责分离。
  • 原生插件没有散落到多个 Vue 页面。
  • Preferences 是持久化来源，Pinia 是响应式副本。
  • Android 不依赖固定开发服务器 URL。
  • appId 在 Gradle、Java package 和资源中一致。

已知限制

  • 所有历史记录存在一个 JSON 中，数据量大时应迁移 SQLite。
  • 设备历史显示当前设备信息，没有保存审计快照。
  • Camera、Filesystem 和跨存储一致性尚未设计实现。
2. TypeScript 审查
  • 没有使用 any。
  • 巡检结果使用联合类型。
  • 草稿和正式记录分开。
  • 提交结果使用 discriminated union。
  • Preferences JSON 以 unknown 进入运行时守卫。
  • 日期字符串、ID 和文件路径仍是普通 string，运行时约束由边界保证。
  • 未来外部 API 数据同样不能只靠 Axios 泛型假装已验证。
3. Vue 与状态管理审查
  • 页面局部草稿没有过早全局化。
  • Store 状态通过 storeToRefs 解构。
  • 历史展示项使用 computed 派生，没有复制第二份可变历史。
  • 初始化、加载、提交和存储错误被区分。
  • 保存按钮在初始化和提交期间禁用。
  • 当前 records 仍可被外部直接修改；业务扩大后可只暴露只读 getter 和 action。
4. 异常处理审查

已经处理

  • 表单字段错误
  • 设备不存在或设备加载失败
  • Preferences get/set 失败
  • 损坏 JSON、未知版本和字段类型错误
  • 初始化期间提交和重复提交
  • 非法日期降级
  • SDK 缺失导致的 Gradle 失败

后续必须处理

  • Camera 取消与权限拒绝
  • Filesystem 写入失败和文件丢失
  • Preferences 元数据成功但照片保存失败
  • Android 13+ 通知权限
  • 应用生命周期中断
5. Android 与安全审查
  • 当前 Manifest 只有 INTERNET，没有提前堆权限。
  • keystore、keystore 文件和 key.properties 已加入忽略。
  • Release 当前未配置签名，不能当作正式发布包。
  • minifyEnabled false 暂时保留，Day 5 再决定 R8/ProGuard。
  • allowBackup=true 是模板默认值，Release 前需根据本地数据敏感性审查。
  • 模板测试包仍为 com.getcapacitor.myapp，不影响主应用，后续可整理。

Android 解释练习

术语 一句话解释 不要混淆
InspectionDraft 用户正在编辑、允许暂时不完整的表单状态 不是可直接进入历史的正式记录
InspectionRecord 通过提交边界后具有 ID、合法结果和时间的实体 不是页面输入对象的简单类型断言
Pinia Vue 应用运行期间的响应式共享状态 不等于持久化数据库
Preferences 跨平台轻量 key/value 持久化 不适合大文件和复杂查询
Capacitor Bridge 连接 WebView JavaScript 与原生插件的桥梁 不是把 Vue 编译成 Java
appId Android/商店识别应用的稳定唯一身份 不同于用户看到的 appName
cap sync 复制 Web 构建产物并更新原生插件与依赖 不同于只创建平台的 cap add
