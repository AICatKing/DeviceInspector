这一阶段你必须学习什么

学习目标不是背语法，而是能根据业务约束设计类型，并解释不同方案的取舍。

基础

联合类型

用有限值表达业务状态，避免任意字符串进入系统。

type Result =
  | 'passed'
  | 'failed'
建模

草稿与实体

编辑状态允许不完整；提交后的业务实体应该满足更严格的约束。

Draft ≠ Record
可选字段 ≠ 必填字段
分层

序列化边界

Pinia、Preferences 和 Filesystem 保存的是不同形态和生命周期的数据。

内存状态
持久化元数据
二进制文件
知识点 必须理解的内容 常见误区 面试表达重点
联合类型 把巡检结果限制为一组合法状态，编译期阻止拼写错误和未知状态。 为了省事全部写成 string。 类型本身就是业务规则的一部分。
interface 与 type 对象结构通常可用接口；联合、映射和组合类型通常更适合 type。 机械争论哪一个“永远更好”。 根据表达目标选择，而不是根据个人口号选择。
可选属性与 null ? 表示可能不存在；null 通常表示字段存在但当前没有值。 在没有语义约定时混用 undefined、null 和空字符串。 统一空值语义能减少表单、存储和接口转换错误。
ISO 时间字符串 持久化和传输时使用稳定、可序列化的格式；展示时再本地化格式化。 直接保存“昨天”或本地化显示文本。 存储格式和展示格式应该分离。
文件引用 业务记录保存照片路径或标识符，照片内容交给 Filesystem。 把 Base64 图片塞进 Preferences。 元数据与大文件分开，便于性能、清理和迁移。
静态类型边界 TypeScript 不会自动验证接口或本地存储里的运行时 JSON。 以为 axios.get<Device[]> 会验证服务端数据。 泛型提供静态提示；不可信数据仍需运行时保护。

设计类型时重点注意

  • 不要先想页面控件，先想业务事实。
  • 不要把所有字段都写成可选，避免把问题推给运行时。
  • 不要为了“复用”强行让草稿和正式记录共用一个宽松接口。
  • 不要在业务类型里直接塞 Capacitor 插件返回的完整对象。
  • 每个状态值都应该能用一句中文解释。

你应该能够讲出的设计理由

  • 为什么结果不是 boolean。
  • 为什么草稿和已提交记录的必填字段不同。
  • 为什么日期存 ISO 字符串而不是直接存 Date。
  • 为什么照片不存 Base64 到 Preferences。
  • 为什么 ID 和提交时间不应该由模板层随意生成。

本模块可能出现的 5 个面试问题

  1. 为什么巡检结果使用联合类型，而不是普通字符串或布尔值？
  2. interface 和 type 在这个项目里分别适合表达什么？
  3. 为什么编辑中的表单模型和已经持久化的巡检记录不应该完全相同？
  4. TypeScript 已经声明了接口类型，为什么从 Preferences 读取 JSON 时仍可能不安全？
  5. 为什么巡检记录只保存照片文件引用，而不直接保存 Base64 图片？

“用自己的话解释”练习题

假设面试官问：“为什么不直接创建一个所有字段都可选的 Inspection 接口，让表单和历史记录都使用它？”请你用 1～2 分钟回答。回答时至少涉及：业务约束、编译期保障、提交边界和后续维护。

先不要找标准答案。完成类型设计后，把你的回答发给导师，再针对错误或遗漏纠正。

关键架构决策：数据怎么存

核心不是“把插件都用一遍”，而是让每种工具承担适合自己的职责。

方案 A：全部存 Preferences

实现最快

优点

  • API 简单
  • 初期代码少
  • 容易快速跑通

问题

  • 不适合存储大体积照片
  • Base64 增加体积和解析成本
  • 职责混乱，难以解释为合理设计

结论：不推荐。

本项目推荐

方案 B：元数据与文件分离

平衡实现与质量

Preferences

  • 巡检记录元数据
  • 用户设置
  • 数据版本号

Filesystem

  • 巡检照片
  • 文件生命周期管理
  • 删除记录时同步清理

结论：五天项目的最佳选择。

方案 C：SQLite + Filesystem

扩展能力最强

优点

  • 适合复杂查询和大量记录
  • 支持索引、分页和关系数据
  • 更容易扩展大型业务

问题

  • 增加插件与 Android 调试成本
  • 五天内投入产出比低
  • 需要解释更多数据库细节

结论：放入未来改进，不在本期实现。

1. 架构审查

做得正确的方向

当前已经形成 View → Pinia Store → Service → Mock 数据 的基础调用链，后续应该保留这个方向。原生能力也应采用页面、Composable/Store、Service、Capacitor Plugin 的分层。

主要问题

  • 设备数据源仍硬编码在 Service 内，数据访问边界还不能方便替换。
  • 缺少最核心的巡检领域模型和持久化策略。
  • 尚未区分业务元数据和原生文件。
  • 还没有统一处理 Web 与 Android 的环境差异。
2. TypeScript 审查

做得较好

  • DeviceStatus 使用联合类型。
  • 状态标签使用 Record<DeviceStatus, string> 保证映射完整。
  • 异常捕获使用 unknown，没有无脑使用 any。
  • 异步函数声明了明确返回类型。

后续关注

  • 约定日期字段必须是 ISO 8601 字符串。
  • 区分“不存在”和“请求失败”等不同错误语义。
  • 理解 TypeScript 不会自动验证外部 JSON。
  • 本地持久化数据要考虑版本和损坏恢复。
3. Vue 使用审查

做得较好

  • 使用 <script setup lang="ts"> 和 Composition API。
  • 使用 storeToRefs() 保持 Pinia 状态响应性。
  • 路由参数通过 props 传入详情页。
  • 列表使用稳定的设备 ID 作为 key。

后续关注

  • 日期格式化逻辑已经在列表和详情重复，历史模块加入前应提取。
  • 设备状态徽章的模板与 CSS 重复，可在合适时机提取小组件。
  • 列表还缺空状态、重试和无网络提示。
  • 详情加载需要考虑路由快速切换时的异步请求竞态。
4. 状态管理审查
  • 列表和详情分别拥有 loading/error，比一个全局 loading 更合理。
  • devices 与 currentDevice 可能形成两份数据来源，需要避免更新不同步。
  • 网络、本地缓存和离线降级加入后，不应把所有策略都堆进 Store。
  • Store 负责响应式业务状态；Service 负责数据访问和平台能力边界。
  • 详情请求需要防止旧请求晚返回后覆盖新页面状态。
5. 异常处理审查

现有的 err instanceof Error 是正确起点，但原生模块会增加很多可区分场景：

  • 用户主动取消拍照
  • 首次拒绝权限或永久拒绝权限
  • 文件写入失败或历史文件已经不存在
  • Preferences JSON 损坏
  • 网络断开
  • Android 13+ 通知权限未授予

这些情况不能全部显示成“操作失败”。我们会随模块逐步建立轻量错误语义，不提前搭建复杂框架。

6. 可维护性审查
  • README 仍是 Vite 模板内容，最终需要改成求职项目文档。
  • 日期和状态样式已有少量重复，但暂时不需要过度抽象。
  • Mock 数据和 Service 实现在同一文件，切换数据源前再拆分。
  • 尚无 ESLint、测试、环境变量约定和目录职责说明。
  • 优先级应是：核心流程 → 原生能力 → 权限异常 → 真机 → Release → 文档。
